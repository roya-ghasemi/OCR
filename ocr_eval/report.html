Reading accuracy

Two failure modes, kept apart from accuracy

CER and WER are measured only on images that actually returned text. The cases where the model returned nothing — a looped, unterminated JSON (422) or a valid-but-empty all-null response — are counted separately, so a robustness problem never disguises itself as a reading score, and vice-versa.

The gap tells the story: Persian-only letters read at 4.5% CER, but the same model on bilingual letters lands at 25.6% — and separately, every one of the 422 hard failures was a bilingual letter, while every empty response was Persian-only.

Where bilingual breaks

Persian script vs. embedded Latin / digits

Splitting each bilingual letter into its Persian-script runs and its Latin/digit runs shows which side is weaker — a single blended number would hide it.

Persian-script runs 16.17%
Latin / digit runs 32.85%

Codes, dates, amounts and account numbers embedded in Persian text are read about twice as unreliably as the surrounding prose. Of 140 Latin/digit runs checked, 32% were misread and one number was cleanly reversed — 0093 → 3900 — the classic RTL/LTR digit-flip.

Normalization sensitivity

The scores aren't a normalization artifact

Persian CER is notoriously sensitive to normalization (ی vs ي, ك vs ک, ZWNJ, digit styles). The same predictions scored three ways barely move, so the headline number is real rather than manufactured by aggressive cleanup.

Raw (whitespace only)17.75%
+ Persian (ی/ک, ZWNJ)17.04%
+ digit style (۰–۹→0–9)17.04%

Persian normalization shaves ~0.7 points (mostly ZWNJ and ی/ک). Digit-style normalization changes nothing here — this set's source numbers are Latin — but it would matter for documents that write numbers in Persian digits.

Character confusion

Most frequent substitutions

Ground-truth → predicted, after normalization. Persian errors are dot/tooth swaps; the noisiest pairs are actually Latin letters being swallowed into Persian glyphs inside bilingual lines.

ی → ه×4 پ → ی×3 م → ن×3 ش → ی×2 پ → ب×2 I → 3×3 0 → 6×3 o → ض×2 i → ی×2 n → ت×2

The one classic Persian dot-confusion that showed up materially is ب/پ. Everything else is spread thin — there's no single systematic Persian misread to fix.

Dictionary correction · Dehkhoda

The first design made it worse. Here's why, and the fix.

All 33 Dehkhoda SQL dumps (312,507 headwords) were loaded into a local SQLite database and wired in as a post-corrector on out-of-vocabulary Persian words. The first version lowered accuracy by a full CER point — so it was treated as a bug and diagnosed rather than accepted.

Root cause — the harmful edits weren't OCR errors at allv1 bug
found 60 harmful substitutions (س→ا ×14, ژ→ت ×11, د→م ×7, ح→ن ×7) — no OCR confuses these; they're typing errors. Plus 10 harmful transpositions and zero helpful ones: transposition is a keyboard artifact OCR never produces.

v1 was built like a spell-checker for typos, allowing any edit across all 35 letters. Real OCR errors are visual — same skeleton, different dots (ب پ ت ث ن ی) or same shape family (ج چ ح خ). v2 restricts the edit model to exactly that.

Correction ruleCERΔhelpfulharmful
no correction (baseline)17.04%———
v1 · any single edit18.08%+1.04%683

v2c · confusable-sub only17.15%+0.11%111
v2d · doubled-letter deletion only ✓17.01%−0.03%20

v2d is now the shipped default — the only rule that never damages a correct word. It fixes doubled-letter artifacts (استحضاار → استحضار) and refuses to guess at anything else. The ~1.07-point regression is fully recovered.

The remaining ceiling is Dehkhoda itself. It's a classical lexicon, so ~22% of correctly-read modern words (سامانه، اینترنت، دیجیتال، پروژه، فناوری) aren't in it. Any rule aggressive enough to fix a real error also snaps those onto classical neighbours — پروژه → پروره is the clearest case and isn't solvable from the dictionary alone. Dropping the 32.8% of entries that are pure cross-references was tested too, and changed nothing.

Conclusion

Where it's strong, where it isn't

Printed Persian is the strong suit

4.5% CER on Persian-only letters, 16.2% on Persian runs inside bilingual ones. As a Persian document reader, it's solid.

Embedded Latin & numbers are the weak spot

32.9% CER on codes, dates, emails and account numbers, with a third of such runs misread and occasional digit reversal. Don't trust an IBAN or invoice number from this without a check digit.

One in six letters returns nothing

16.7% produce no usable text — bilingual ones loop into invalid JSON, Persian ones sometimes come back empty. Catching the 422/empty and retrying with a higher token budget would recover most.

Dehkhoda correction: fixed, but its ceiling is low

The first corrector raised CER by a point because it modelled typing errors instead of visual ones. Restricted to OCR-plausible edits it is now safe (17.04% → 17.01%, zero harmful changes) — but a classical lexicon can only do so much when a fifth of modern vocabulary is missing from it. Next: a modern frequency lexicon, confidence-gated correction, and a checksum validator for codes.

The numbers are honest

Raw-to-normalized CER moves only 17.75% → 17.04%, so nothing here is an artifact of aggressive Persian normalization.
